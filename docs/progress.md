### 3. Ответы на контрольные вопросы к защите ЛР 3

**1. Почему состояние сущностей хранится в `App.tsx`, а не в `MoviesPage`?**  
Потому что данные о фильмах требуются сразу нескольким независимым страницам: `MoviesPage` (для отображения и фильтрации каталога), `NewMoviePage` (для добавления нового фильма), `MovieDetailsPage` (для просмотра и удаления по id) и `EditMoviePage` (для редактирования). В React данные передаются сверху вниз (one-way data binding). Чтобы разные ветви дерева компонентов могли читать и модифицировать одни и те же данные, состояние поднимается к их ближайшему общему предку — паттерн **Lifting State Up** (подъем состояния).

**2. В чем разница между управляемым и неуправляемым компонентом формы?**  
В **управляемом компоненте** значение поля формы хранится в React-состоянии (`value={draft.title}`) и изменяется через обработчик (`onChange`). React является «единственным источником правды» (single source of truth).  
В **неуправляемом компоненте** значение хранится непосредственно в DOM-дереве браузера, а доступ к нему React получает через `ref` только в момент отправки формы.

**3. Зачем использовать функциональное обновление состояния `setMovies(prev => ...)`?**  
Обновления состояния в React могут происходить асинхронно и пакетироваться (batching). Когда новое состояние вычисляется на основе предыдущего (добавление, изменение или удаление элемента массива), передача колбэка `prev => ...` гарантирует, что мы работаем с самым актуальным состоянием, избегая состояния гонки (race condition).

**4. Почему нельзя мутировать массив в состоянии (`movies.push()`, `movie.title = ...`)?**  
React отслеживает изменения состояния по ссылке на объект (shallow equality check: `Object.is(oldState, newState)`). Если мутировать существующий массив методом `.push()` или изменить свойство объекта напрямую, ссылка в памяти останется прежней. React посчитает, что ничего не изменилось, и не запустит повторный рендеринг (re-render) интерфейса. Для обновления всегда создаются новые массивы и объекты (через спред `[...prev]`, `.map()`, `.filter()`).

**5. Почему для кнопки «Отмена» обязательно указывать `type="button"`?**  
В HTML по умолчанию кнопка внутри формы `<form>` имеет тип `type="submit"`. Если не указать `type="button"`, клик по кнопке «Отмена» вызовет событие отправки формы (`onSubmit`), сработает валидация или нежелательное сохранение. `type="button"` гарантирует, что кнопка только выполнит свой `onClick` без отправки формы.

**6. Зачем указывать `key={movie.id}` при рендере `<MovieForm>` на странице редактирования?**  
Если пользователь переходит со страницы редактирования одного фильма на страницу редактирования другого (например, по внешней ссылке), компонент `MovieForm` не будет размонтирован, а его внутреннее состояние `draft` (инициализированное при первом рендере) не обновится само собой. Атрибут `key` сообщает React, что перед ним другой экземпляр компонента, заставляя React полностью сбросить и перемонтировать форму с новыми начальными данными.

**7. В чем разница между клиентской и серверной валидацией?**  
**Клиентская валидация** происходит мгновенно в браузере пользователя прямо перед отправкой (дает быстрый отклик, экономит трафик и ресурсы сервера). Однако клиентский код можно обойти (отключив JS или отправив запрос напрямую через Postman/curl).  
**Серверная валидация** — обязательный и окончательный рубеж безопасности, гарантирующий целостность и корректность данных в базе данных.

**8. Почему при перезагрузке страницы (F5) данные сбрасываются?**  
Потому что в данной лабораторной работе данные хранятся исключительно в оперативной памяти (RAM) процесса JavaScript в браузере (React state). При нажатии F5 браузер полностью выгружает текущую веб-страницу из памяти и загружает приложение заново с начальными значениями из кода. Постоянное хранение будет реализовано в следующих работах при подключении Supabase / бэкенда.
